# Spec: Invite-based enrollment with mandatory MFA (local accounts)

**Date:** 2026-06-07
**Project:** Authentik SSO (`/home/pi/Projects/Docker/Authentik`)
**Status:** Approved (per user workflow — design pre-approved)

## Goal

Let an operator invite specific people to self-register an Authentik account via a
single-use, expiring link. Signup forces account creation with mandatory MFA, and
drops the new user into the group the invite was issued for. Local accounts only in
this iteration; "Sign up with Google" is a deferred follow-up.

## Scope

**In scope**
- Rename group `admin` → `super-admin` (two groups total: `super-admin`, `streaming`).
- One **enrollment flow**, gated by **invitation required** (no open registration).
- Local account creation: username, email, name, password.
- **Mandatory MFA** during enrollment — user chooses **TOTP** (authenticator app) **or**
  **WebAuthn passkey**; signup cannot complete without one.
- **Single-use invitations**, each with an **expiry** and a **target group**
  (`super-admin` or `streaming`) carried in `fixed_data`.
- New user is added to the invite's target group automatically.
- Everything declared in the blueprint (config-as-code).

**Out of scope (deferred)**
- Google / social sign-up (separate follow-up — needs a Google Cloud OAuth client).
- Reusable / multi-use invite links (single-use only for now).
- Email verification of the address entered (can add an email stage later).
- Self-service password reset / recovery flow changes.

## Decisions (from brainstorming)

| Question | Decision |
|---|---|
| `super-admin` vs existing `admin` | **Rename** `admin` → `super-admin` (same meaning) |
| Google login | **Local-only now**, Google later |
| Invite link type | **Single-use per person** (expiry + target group each) |
| MFA on signup | **Mandatory**, user picks **TOTP or WebAuthn passkey** |
| Group-from-invite mechanism | **One flow**, group read from invite `fixed_data` (Approach A) |

## Group rename — ripple

Renaming the Authentik group touches three existing blueprint items:
1. The group entry: `admin` → `super-admin`.
2. ABS role-claim scope mapping: membership check `ak_is_group_member(user, name="super-admin")`.
   The **emitted** claim value stays `["admin"]` / `["user"]` so the (not-yet-done) ABS
   OIDC config maps "admin" → ABS Admin role unchanged.
3. Access bindings: Portainer (super-admin only) and ABS (super-admin + streaming).

No users exist in `admin` yet, so the stale group is deleted — no migration needed.

## Enrollment flow — stages (in order)

1. **Invitation stage** — `continue_flow_without_invitation = false` (token required).
   Reads the invite's `fixed_data` into the flow context.
2. **Prompt stage** — fields: `username`, `email`, `name`, `password`, `password_repeat`.
3. **User-write stage** — creates an internal user from the prompt data.
4. **Group assignment** — expression policy (or equivalent) that reads the target group
   from the invitation `fixed_data` and adds the freshly-created user to it.
5. **Authenticator validation stage** — device classes `[totp, webauthn]`,
   `not_configured_action = configure`, configuration stages = TOTP-setup + WebAuthn-setup.
   Forces the user to enrol one factor.
6. **User-login stage** — establishes the session.

Flow designation: `enrollment`. Not linked from the login page → reachable only via an
invite token, so there is no open self-registration.

## Invitations

- Model: `authentik_stages_invitation.invitation`.
- `single_use = true`.
- `expires` = per-invite valid-until timestamp.
- `fixed_data = {"group": "super-admin"}` or `{"group": "streaming"}`.
- Generated by the operator in **Directory → Invitations → Create** (pick the enrollment
  flow, set expiry, set `fixed_data`), or via an API/CLI one-liner.
- Invite URL: `https://sso.holy-grail.ch/if/flow/<enrollment-flow-slug>/?itoken=<token>`.

## Architecture / data flow

```
operator → creates Invitation(single_use, expires, fixed_data={group}) → hands link to invitee
invitee  → opens link (?itoken=...)
         → Invitation stage validates token, loads fixed_data
         → Prompt (username/email/name/password)
         → User-write (create user)
         → Group assignment (add to fixed_data.group)
         → Authenticator validation (must set up TOTP or WebAuthn)
         → User-login (session established)
```

## Testing / verification

Authentik flows aren't unit-testable; verify by exercising the live flow:
- Blueprint applies cleanly (`status: successful`); flow + stages + bindings exist (API check).
- Create a `streaming` invite → open link → confirm: token required (no token = denied),
  account created, MFA enrollment forced, user lands in `streaming`, can log in.
- Create a `super-admin` invite → confirm user lands in `super-admin`.
- Confirm an expired/used token is rejected.
- Confirm renamed group: Portainer access = super-admin only; ABS = super-admin + streaming.

## Risks / notes

- Group rename via blueprint creates the new group and orphans the old `admin`; the plan
  must delete the stale group (safe — empty).
- The "TOTP or WebAuthn" choice depends on the authenticator-validation stage's
  `configure` behaviour offering both setup stages — verify in the live flow.
- Keep it standard: use Authentik's built-in enrollment/invitation/authenticator stages,
  no bespoke mechanisms. (See [[prefer-standard-over-custom-hardening]].)
